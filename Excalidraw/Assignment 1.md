Overview  ^XKbl3v7D

On selection — the greedy knapsack by efficiency score (penalty/cost) is the right approach. Industry guidance recommends monitoring small file count through Iceberg's metadata tables and triggering compaction when the count exceeds a threshold that noticeably affects query performance, which is exactly what the trigger conditions encode. ^ZuL0Hq2y

The core insight from research is that the problem has two distinct sub-problems that most people conflate: which partitions to compact (the selection problem), and how to compact each one (the strategy problem). Your deliverable needs both. ^uH9kyCzi

On strategy assignment — the three strategies have meaningfully different cost/benefit profiles. Bin-pack is the cheapest and fastest, combining files using the bin-packing approach with no data ordering or shuffling; Sort is much more expensive but provides total hierarchical ordering so read queries benefit when filtering on ordered columns; Z-order is the most expensive of the three and is best when queries can prune data across multiple dimensions simultaneously ^LYESrxPV

Strategy decision tree - How to compact 
 ^cVPluQLE

IF delete_ratio > 0.30 AND avg_file_size >= 128 MB:
    → SORT compaction
      Reason: Large, high-delete partitions benefit most from row-level reordering;
      sort produces tighter min/max stats, enabling column pruning on future reads.
      Sorting also absorbs delete files in a single pass.

ELSE IF small_file_count / file_count > 0.60 OR avg_file_size < 50 MB:
    → BIN-PACK compaction
      Reason: Severe fragmentation — primary goal is file consolidation, not layout.
      Bin-pack is the cheapest and fastest strategy; no shuffle required.
      Resolves I/O overhead immediately.

ELSE IF delete_ratio > 0.10 AND partition_access_frequency > 600:
    → Z-ORDER compaction
      Reason: Hot partitions with moderate deletes benefit from multi-dimensional
      clustering. Queries that filter on multiple columns prune more files.
      AWS benchmarks show 3× gains vs bin-pack on multi-filter workloads.

ELSE:
    → BIN-PACK compaction (default)
      Reason: No dominant degradation signal; bin-pack is safest and cheapest. ^TuNPUfyF

Goal: File size consolidation only. No row reordering or shuffle.

Cost: Cheapest. Reads + writes only. No global sort.

Best for: Severely fragmented partitions, streaming-ingested tables,
 any partition where file count is the primary issue.

Goal: File consolidation + hierarchical row ordering by specified columns. ^3yczg4BW
