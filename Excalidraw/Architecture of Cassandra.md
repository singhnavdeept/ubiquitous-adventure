### Core Concept ^d8imQfC2

Data is stored **column-by-column** rather than row-by-row. ^rqjr6tVx

**Row Store (Postgres):** ^Wcj35iYa

`Row1: [ID1, Name1, Age1, Salary1]` -> `Row2: [ID2, Name2, Age2, Salary2]` ^LOU4y9ek

*Good for: Fetching everything about ID1.* ^bZwTSJdr

**Column Store (ClickHouse, Snowflake, Parquet):** ^0jt8GSg8

`File1 (ID): [1, 2, 3, 4, 5]` ^9iMoNPQb

`File2 (Name): [Alice, Bob, Carol...]` ^I5nr66M9

*Good for: Calculating the average Salary of all 5 million rows.* ^uxf8lwPI

### The Physics ^B3tNzkTQ

- **Vectorized Execution:** The CPU doesn't have to skip over `Name` and `Address` bytes to get to the next `Salary` value. It reads a dense, compressed block of *only* `Salary` integers. This saturates L1/L2 CPU cache and enables[[ SIMD (Single Instruction, Multiple Data) ]]processing. ^3CbhbNhH

- **Compression Ratios:** Columnar compression is insane. A column containing "United States" 9 million times can be compressed via dictionary encoding to a single integer ID. Storage footprint drops by 90%+ compared to row-based. ^PyETPTwe

### When to Use (The Sweet Spot) ^camwkshX

- **Aggregate Queries:** `SELECT AVG(revenue) FROM sales WHERE date > '2025-01-01'` ^nomiZ20W

- **Time Series Data:** Appending new columns of metrics. ^NxSK3UNd

- **Data Warehousing (OLAP).** ^dEaaFzOP

**Point Updates / Single Row Selects.** Updating a specific row in a column store is an operational nightmare (it requires rewriting multiple column files). Fetching all attributes of a single user (`SELECT * FROM users WHERE id = 123`) is **much slower** than a row store because the DB must reconstruct the row from 5 separate column files. **Never use a column store as your primary transactional application database.** ^usiRqXDw
