This is where SQL stops being a simple reporting language and becomes a **multi-dimensional analytical engine**. `ROLLUP`, `CUBE`, and `GROUPING SETS` are the tools you use when someone asks for "Totals, Subtotals, and Grand Totals" in a single query rather than 47 separate `UNION ALL` statements.

These notes assume you understand basic `GROUP BY`. We're now operating in the **OLAP** (Online Analytical Processing) layer of the database.

# Comprehensive Engineering Notes: Advanced Aggregation (ROLLUP, CUBE, GROUPING SETS)

## The Core Problem: The Explosion of Subtotals

Imagine you are analyzing the `sales_transactions` dataset from our previous lesson. The business asks for:
1. Total sales by `(region, product_category)`.
2. Total sales by `(region)`.
3. Total sales by `(product_category)`.
4. **Grand total** of all sales.

Without advanced aggregation, you write **4 queries and UNION them**:
```sql
-- Painful, slow, and repetitive
SELECT region, product_category, SUM(amount) FROM sales GROUP BY region, product_category
UNION ALL
SELECT region, NULL, SUM(amount) FROM sales GROUP BY region
UNION ALL
SELECT NULL, product_category, SUM(amount) FROM sales GROUP BY product_category
UNION ALL
SELECT NULL, NULL, SUM(amount) FROM sales;
```
This scans the table **4 times**. With a 10TB table, that's a resume-generating event.

`GROUPING SETS` (and its syntactic sugar `ROLLUP` and `CUBE`) solve this by **computing multiple grouping levels in a single pass over the data**.

---

## 1. GROUPING SETS (The Explicit Foundation)

### Definition
`GROUPING SETS` allows you to specify **exactly** which combinations of columns you want to aggregate.

### Syntax
```sql
SELECT region, product_category, SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY GROUPING SETS (
    (region, product_category),  -- Level 1: Most granular
    (region),                    -- Level 2: Region subtotal
    (product_category),          -- Level 3: Category subtotal
    ()                           -- Level 4: Grand total (empty set)
)
ORDER BY region, product_category;
```

### Output (Partial)
| region | product_category | total_sales |
| :--- | :--- | :--- |
| East | Office | 200.00 |
| East | **NULL** | **200.00** |
| North | Electronics | 800.00 |
| North | Furniture | 4200.00 |
| North | **NULL** | **5000.00** |
| South | Electronics | 925.00 |
| South | Furniture | 950.00 |
| South | **NULL** | **1875.00** |
| **NULL** | Electronics | 1725.00 |
| **NULL** | Furniture | 5150.00 |
| **NULL** | Office | 200.00 |
| **NULL** | **NULL** | **7075.00** |

### The `NULL` Problem: Distinguishing "Subtotal" from "Missing Data"
Notice the `NULL` values in the output. A `NULL` in `region` means **"This row is a subtotal across all regions."** But what if the original data legitimately contained a `NULL` region? You can't tell the difference.

**The Solution: `GROUPING()` Function**
`GROUPING(column)` returns **1** if the column is aggregated in the current row (i.e., the `NULL` represents a subtotal), and **0** if it's an actual data value.

```sql
SELECT 
    CASE WHEN GROUPING(region) = 1 THEN 'ALL REGIONS' ELSE region END AS region_label,
    CASE WHEN GROUPING(product_category) = 1 THEN 'ALL CATEGORIES' ELSE product_category END AS category_label,
    SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY GROUPING SETS ((region, product_category), (region), (product_category), ())
ORDER BY region, product_category;
```

**Engineer's Note:** In Microsoft T-SQL, use `GROUPING_ID()` which returns a bitmask of which columns are aggregated. In modern PostgreSQL, you can just use the `GROUPING` function.

## 2. ROLLUP (Hierarchical Drill-Down)

### Definition
`ROLLUP(a, b, c)` generates **n+1** grouping sets, moving from right to left:
1. `(a, b, c)` – Full detail
2. `(a, b)` – Subtotal by `a, b`
3. `(a)` – Subtotal by `a`
4. `()` – Grand total

It represents a **strict hierarchy**. You use `ROLLUP` when the dimensions have a parent-child relationship (e.g., **Year > Quarter > Month** or **Country > State > City**).

### Example: Sales by Region and Rep
**Goal:** See sales per `(region, rep)` with subtotals by `region` and a grand total.

```sql
SELECT 
    region, 
    rep, 
    SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY ROLLUP (region, rep)
ORDER BY region, rep;
```

### Output
| region | rep | total_sales |
| :--- | :--- | :--- |
| East | Eve | 200.00 |
| East | **NULL** | **200.00** |
| North | Alice | 800.00 |
| North | Bob | 4200.00 |
| North | **NULL** | **5000.00** |
| South | Carol | 925.00 |
| South | Dave | 950.00 |
| South | **NULL** | **1875.00** |
| **NULL** | **NULL** | **7075.00** |

### How It Works Internally
`ROLLUP (region, rep)` is **equivalent** to:
```sql
GROUP BY GROUPING SETS (
    (region, rep),
    (region),
    ()
)
```

### The Partial ROLLUP Trick
You can combine `ROLLUP` with standard `GROUP BY` columns.
```sql
-- Compute subtotals by region and date, but always keep product_category fixed
GROUP BY product_category, ROLLUP (region, sale_date)
```
This generates sets: `(product, region, date)`, `(product, region)`, `(product)`.

## 3. CUBE (The Cross-Tabulation Monster)

### Definition
`CUBE(a, b, c)` generates **2^n** grouping sets. It computes the **Cartesian product** of all possible aggregations: every combination of columns being present or absent in the grouping.

### Example: CUBE(region, product_category)
This generates **4** sets (2^2):
1. `(region, product_category)` – Detail
2. `(region)` – Region totals
3. `(product_category)` – Category totals
4. `()` – Grand total

```sql
SELECT 
    region, 
    product_category, 
    SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY CUBE (region, product_category)
ORDER BY region, product_category;
```

### Output (Same as GROUPING SETS example earlier)
The output includes:
- Rows with `NULL` in region but `Electronics` -> Category subtotal across all regions.
- Rows with `NULL` in category but `North` -> Region subtotal across all categories.
- Rows with both `NULL` -> Grand total.

### The Exponential Danger
`CUBE (d1, d2, d3, d4)` generates **16** grouping sets.
`CUBE (d1, d2, d3, d4, d5)` generates **32** grouping sets.

**Never use CUBE on 10 dimensions unless you want to melt your database server.** For high-dimensional data, use `CUBE` only on the 2-3 dimensions you *actually* need all combinations of.

### When to Use CUBE vs. ROLLUP

| Scenario | Use | Reason |
| :--- | :--- | :--- |
| "Sales by Country, State, City" | **ROLLUP** | There is a strict hierarchy. A City belongs to exactly one State. |
| "Sales by Product Category and Customer Segment" | **CUBE** | No hierarchy. You want to see "Electronics sold to Students" AND "All Electronics" AND "All Sales to Students" independently. |

## 4. Performance & Engineering Considerations

### The Single-Scan Advantage
The database optimizer translates `GROUPING SETS`, `ROLLUP`, and `CUBE` into a **single pass** over the data (or a single hash aggregate phase). It builds multiple hash tables in memory simultaneously or writes to multiple spill files in one go. This is **dramatically** faster than `UNION ALL`.

### Execution Plan Details (PostgreSQL)
```sql
EXPLAIN SELECT ... GROUP BY ROLLUP(region, product);
```
You'll see a node called **`MixedAggregate`** or **`GroupAggregate`** with `Group Key` sets listed. It's doing the work in one pipeline.

### Memory Pressure
Each grouping set requires its own hash table (or sort buffer). If you have `CUBE(a,b,c,d)`, the database might need **8 separate hash tables** in memory.
- **Work_mem / Hash_mem_multiplier:** Ensure this is tuned. If the hash tables spill to disk, performance tanks.
- **Column Projection:** Only include the columns you *actually* need in the `GROUP BY`. Extra columns inflate the hash table keys.

### The Materialized Alternative
If you're using a database that doesn't support these clauses well (looking at you, older MySQL), you can **pre-aggregate** with a CTE:
```sql
WITH base AS (
    SELECT region, product, SUM(amount) AS total
    FROM sales GROUP BY region, product
)
SELECT region, product, total FROM base
UNION ALL
SELECT region, NULL, SUM(total) FROM base GROUP BY region
UNION ALL ...
```
This avoids scanning the giant raw table multiple times, but it still requires multiple passes over the *aggregated* result.

## 5. Real-World Use Case: The Pivot Table Backend

Imagine you're building an Excel-like pivot table interface for an analytics dashboard. The user drags "Region" to Rows, "Product Category" to Columns, and "SUM(Amount)" to Values.

Your backend API needs to return a flat dataset that the frontend can pivot into:

| | Electronics | Furniture | Office | **Total** |
| :--- | :--- | :--- | :--- | :--- |
| **North** | 800 | 4200 | 0 | 5000 |
| **South** | 925 | 950 | 0 | 1875 |
| **East** | 0 | 0 | 200 | 200 |
| **Total** | 1725 | 5150 | 200 | 7075 |

**The Query:**
```sql
SELECT 
    COALESCE(region, 'Total') AS region,
    COALESCE(product_category, 'Total') AS product_category,
    SUM(amount) AS total_sales
FROM sales_transactions
GROUP BY CUBE (region, product_category);
```
This **single query** produces every cell in that pivot table, including row totals, column totals, and the grand corner total.

## 6. Pitfalls & Anti-Patterns

### 1. Filtering Out Subtotal Rows Incorrectly
```sql
-- WRONG: This removes actual NULL data too
WHERE region IS NOT NULL 

-- CORRECT: Use GROUPING function
WHERE GROUPING(region) = 0
```

### 2. ORDER BY Confusion
When you have `NULL` placeholders for subtotals, `ORDER BY region` puts the subtotal row **last** (because `NULL` sorts high by default in PostgreSQL).
```sql
-- Force subtotals to appear after their detail rows
ORDER BY 
    GROUPING(region), region,   -- 0 (detail) before 1 (subtotal)
    GROUPING(product_category), product_category;
```

### 3. Over-CUBING
`CUBE(year, month, day, hour, minute)` is 32 grouping sets. You will never analyze data at the `minute` granularity across all `years`. It's computationally wasteful. Use `ROLLUP` for time hierarchies, or explicitly limit with `GROUPING SETS`.

## Summary Cheat Sheet

| Clause | Grouping Sets Generated | Use Case |
| :--- | :--- | :--- |
| `GROUPING SETS (...)` | **User-defined** list | Precise control over which subtotals you need. |
| `ROLLUP(a, b, c)` | `(a,b,c)`, `(a,b)`, `(a)`, `()` | Hierarchical drill-down (Geography, Time). |
| `CUBE(a, b)` | `(a,b)`, `(a)`, `(b)`, `()` | Cross-tabulation of independent dimensions. |

**The Golden Rule:**
*If you find yourself writing `UNION ALL` to combine different `GROUP BY` queries on the same table, stop. You are almost certainly looking at a `GROUPING SETS` problem. Let the database do the heavy lifting in one pass.*
