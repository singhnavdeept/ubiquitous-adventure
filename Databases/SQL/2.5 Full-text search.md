This is where databases stop being simple "string matchers" and start being **search engines**. When `LIKE '%keyword%'` brings your production database to its knees, full-text search (FTS) is the escape hatch. This is not a simple pattern match; it is a **linguistic pipeline** that understands word stems, ignores "the" and "a," and ranks documents by relevance.

These notes cover the mechanics of FTS in PostgreSQL (the gold standard for integrated FTS), but the concepts translate to SQL Server, MySQL, and Oracle.

---

# Comprehensive Engineering Notes: PostgreSQL Full-Text Search

## 1. The FTS Pipeline: From Raw Text to Searchable Data

Before we touch `tsvector` and `tsquery`, you must understand the **transformation pipeline**. This is the "magic" that makes "running" match "run".

```text
Raw Document Text: "The quick brown foxes jumped over the lazy dogs."
        |
        v
[ Parser ]           Breaks text into tokens: "The", "quick", "brown", "foxes", ...
        |
        v
[ Dictionaries ]     Normalizes tokens to lexemes:
                     - Stop words removed: "The", "over", "the" -> discarded
                     - Stemming applied: "foxes" -> "fox", "jumped" -> "jump"
        |
        v
[ tsvector ]         'brown':3 'dog':11 'fox':4 'jump':5 'lazi':10 'quick':2
```

This pipeline is governed by a **Text Search Configuration** (e.g., `english`), which dictates the parser, dictionaries, and stop-word list used.

## 2. The Core Data Types

### 2.1 `tsvector`: The Searchable Document

A `tsvector` is a **sorted list of distinct lexemes** (normalized words) with their positions in the original document.

```sql
SELECT to_tsvector('english', 'The Fat Cats Ate The Rats');
-- Returns: 'ate':4 'cat':2 'fat':1 'rat':5
```

**Engineering Insights:**
- **Stop Words Are Gone:** Common words like "The" and "A" are discarded because they occur too frequently to be useful for search relevance.
- **Stemming Applied:** "Cats" becomes "cat", "Ate" becomes "ate".
- **Positions Matter:** The numbers (`:1`, `:2`) are critical for **phrase search** (`<->` operator) and **proximity ranking** (`ts_rank_cd`).
- **Weights (A, B, C, D):** You can assign weights to lexemes from different parts of a document (title vs. body) to influence ranking.

### 2.2 `tsquery`: The Search Query

A `tsquery` stores lexemes to search for, combined with Boolean operators.

| Function | Purpose | Example Input | Resulting `tsquery` |
| :--- | :--- | :--- | :--- |
| `to_tsquery()` | Explicit operators (`&`, `\|`, `!`) | `'fat & cat'` | `'fat' & 'cat'` |
| `plainto_tsquery()` | Implicit AND of all words | `'fat cat'` | `'fat' & 'cat'` |
| `phraseto_tsquery()` | Phrase search (words in order) | `'fat cat'` | `'fat' <-> 'cat'` |
| `websearch_to_tsquery()` | Web syntax (quotes, "or", -) | `'"fat cat" or dog'` | `'fat' <-> 'cat' \| 'dog'` |

**Pro Tip:** `websearch_to_tsquery()` is the best choice for user-facing search boxes because it handles natural syntax like quotes for exact phrases and `-` for exclusion.

### 2.3 The `@@` Match Operator

This is the core of every FTS query. It returns `true` if the `tsvector` matches the `tsquery`.

```sql
SELECT to_tsvector('fat cats ate rats') @@ to_tsquery('cat & rat'); -- true
```

## 3. Indexing: The Performance Layer

FTS without an index scans every row and computes `to_tsvector()` on the fly. **This is a non-starter for production.**

### 3.1 The GIN Index (Standard Choice)

```sql
CREATE INDEX idx_fts ON articles USING gin(to_tsvector('english', body));
```

A GIN index is an **inverted index**: each lexeme maps to a sorted list of row IDs containing it.

**When the Query Runs:**
1. `WHERE to_tsvector('english', body) @@ to_tsquery('cat & rat')`
2. GIN retrieves posting lists for `'cat'` and `'rat'`.
3. The lists are **intersected** (streaming merge) to find rows containing both.
4. Only those rows are returned.

**Critical GIN Configuration Parameters:**
- **`fastupdate` (default: on):** Buffers new index entries in a pending list to speed up individual inserts. The trade-off is that the pending list must be cleaned up periodically, either by autovacuum or a foreground operation.
- **`gin_pending_list_limit`:** The size threshold at which the pending list is flushed. Increase this for write-heavy tables to reduce foreground cleanup stalls.
- **Bulk Inserts:** For loading millions of rows, **drop the GIN index, load data, then recreate it**. This is orders of magnitude faster than incremental updates.

### 3.2 GiST vs. GIN

| Feature | GIN | GiST |
| :--- | :--- | :--- |
| **Write Speed** | Slower (updates are distributed) | Faster |
| **Read Speed** | Faster (precise lexeme lookup) | Slower (may have false positives) |
| **Size** | Larger (2-3x) | Smaller |
| **Best For** | Read-heavy catalogs, rarely updated text | Frequently updated text, spatial data |

**Verdict:** Use **GIN** unless you have a write-heavy workload (e.g., live comment feeds).

### 3.3 The RUM Extension: Beyond GIN

RUM (an extension) is a GIN variant that stores **positional information** inside the index. This eliminates the need for a **heap fetch** when doing phrase search (`<->`) or proximity ranking (`ts_rank_cd`).

**Use Case:** You have millions of documents and users frequently search for exact phrases. RUM makes `phraseto_tsquery()` 10-100x faster.

## 4. Relevance Ranking: Ordering Results Intelligently

Matching is binary (true/false). Ranking is a **float** that answers: *"How good is this match?"*

### 4.1 `ts_rank()`: Frequency-Based

```sql
SELECT title, ts_rank(to_tsvector(body), query) AS rank
FROM articles
WHERE to_tsvector(body) @@ query
ORDER BY rank DESC;
```

`ts_rank()` computes relevance based on **term frequency**:
- How many times does the query term appear?
- How close are the query terms to each other?

### 4.2 `ts_rank_cd()`: Cover Density (Recommended)

`ts_rank_cd()` uses a **cover density algorithm**: it looks for the smallest contiguous span of text that contains all query terms. A tighter "cover" yields a higher score.

**When to Use:**
- **`ts_rank()`:** Simple queries with one or two keywords.
- **`ts_rank_cd()`:** Multi-word queries where proximity matters (e.g., `'machine learning'`). It penalizes documents where the words are far apart.

### 4.3 Normalization: Preventing Long Documents from Dominating

Both ranking functions accept a **bitmask integer** to adjust scores based on document length. Without normalization, a 10,000-word document that mentions "database" 5 times outranks a 200-word document that mentions it 4 times.

| Bitmask | Effect | Use Case |
| :--- | :--- | :--- |
| `0` | No normalization (default) | All documents are similar length |
| `1` | Divide by 1 + log(document length) | General-purpose (recommended) |
| `2` | Divide by document length | Strong penalty for long documents |
| `4` | Divide by mean harmonic distance between extents (`ts_rank_cd` only) | Proximity emphasis |
| `8` | Divide by number of unique words | Punish verbose documents |
| `16` | Divide by 1 + log(unique words) | Moderate verbosity penalty |
| `32` | Divide by (rank + 1) | Cosmetic: scales scores to 0.0-1.0 |

**Practical Recommendation:**
```sql
ts_rank_cd(to_tsvector('english', body), query, 1)  -- 1 = divide by 1+log(length)
```
This ensures a short, dense document isn't unfairly buried by a long, rambling one.

## 5. Advanced Patterns & Techniques

### 5.1 Phrase Search (`<->` and `<N>`)

Introduced in PostgreSQL 9.6, the `<->` (FOLLOWED BY) operator requires lexemes to appear consecutively.

```sql
-- Find "machine learning" as a phrase
SELECT * FROM articles
WHERE to_tsvector('english', body) @@ phraseto_tsquery('english', 'machine learning');
```

`phraseto_tsquery()` handles stop words intelligently by inserting `<N>` operators:
- `phraseto_tsquery('english', 'Juliet and the Licks')` → `'juliet' <3> 'lick'`
- This means "lick" must be the **third** lexeme after "juliet" (accounting for the stop word "the").

### 5.2 Weighted Fields: Title > Body

You can assign **weights** (A, B, C, D) to different parts of a document. Title matches should count more than body matches.

```sql
-- Create a tsvector with weights
UPDATE articles SET fts_doc =
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(body, '')), 'D');

-- Query: A match in the title will score much higher
SELECT title, ts_rank('{0.1, 0.2, 0.4, 1.0}', fts_doc, query) AS rank
FROM articles
WHERE fts_doc @@ query;
```

The weights array `{0.1, 0.2, 0.4, 1.0}` maps to `{D, C, B, A}`. In this example, an A-weight match is worth **10x** a D-weight match.

### 5.3 Highlighting Results (`ts_headline()`)

`ts_headline()` generates an HTML snippet showing where the match occurred, with `<b>` tags around query terms.

```sql
SELECT ts_headline('english', body, query, 'StartSel=<mark>, StopSel=</mark>, MaxFragments=3')
FROM articles
WHERE to_tsvector('english', body) @@ query;
```

**Performance Warning:** `ts_headline()` **re-parses the original document text**. It does **not** use the pre-computed `tsvector`. For production, use a **stored `tsvector` column** and call `ts_headline()` only on the final paginated result set (e.g., top 20 rows), never on the full result set.

### 5.4 Stored Generated Columns (The Right Way)

Do **not** call `to_tsvector()` in the `WHERE` clause of a production query. Create a **generated column** and index it.

```sql
ALTER TABLE articles ADD COLUMN fts_doc tsvector
    GENERATED ALWAYS AS (to_tsvector('english', coalesce(title, '') || ' ' || coalesce(body, ''))) STORED;

CREATE INDEX idx_articles_fts ON articles USING gin(fts_doc);

-- Now queries are clean and always hit the index
SELECT * FROM articles WHERE fts_doc @@ plainto_tsquery('english', 'database tuning');
```

## 6. Production Checklist & Performance Tuning

| Step | Action | Why |
| :--- | :--- | :--- |
| 1 | **Use `GENERATED ALWAYS ... STORED` column** | Avoids recomputing `to_tsvector()` on every query |
| 2 | **Create a GIN index on the `tsvector` column** | Enables fast lexeme lookup |
| 3 | **Set `gin_pending_list_limit` appropriately** | Prevents write stalls on busy tables (e.g., `SET (gin_pending_list_limit = 4096)`) |
| 4 | **Configure `maintenance_work_mem` for index builds** | GIN index creation is memory-intensive; don't skimp |
| 5 | **Use `plainto_tsquery()` or `websearch_to_tsquery()` for user input** | Prevents syntax errors from user input |
| 6 | **Call `ts_headline()` only on the final paginated rows** | Avoids re-parsing the entire result set |
| 7 | **Set `gin_fuzzy_search_limit` for common-word queries** | Prevents a query for "the" from returning 10 million rows and freezing the server |
| 8 | **Consider RUM extension for phrase-heavy workloads** | Eliminates heap fetches for phrase search |

**`gin_fuzzy_search_limit` in Detail:**
When a user searches for a very common word (e.g., "database" in a tech blog), a GIN index scan might return 100,000 rows. Sorting and ranking that many rows can be expensive. Setting `gin_fuzzy_search_limit = 5000` tells PostgreSQL: *"Return a fast, random subset of ~5000 rows, then stop."* The user still gets results, and your database doesn't melt.

## 7. Comparison: FTS vs. Trigram Similarity (`pg_trgm`)

| Feature | Full-Text Search (`tsvector`) | Trigram (`pg_trgm`) |
| :--- | :--- | :--- |
| **What it does** | Linguistic matching (stems, stop words) | Fuzzy string matching (typo tolerance) |
| **"running" matches "run"?** | **Yes** (stemming) | No |
| **"database" matches "databse"?** | No | **Yes** (typo) |
| **Best for** | Natural language search, document retrieval | Username search, autocomplete, typo correction |

**Often used together:** FTS for relevance-ranked document search; trigram for "Did you mean...?" suggestions.

## Summary: The 30-Second FTS Engineering Checklist

1.  **Schema:** Add a `GENERATED ALWAYS ... STORED` `tsvector` column.
2.  **Index:** `CREATE INDEX ... USING gin(fts_column)`.
3.  **Query:** `WHERE fts_column @@ websearch_to_tsquery('english', :user_input)`.
4.  **Rank:** `ORDER BY ts_rank_cd(fts_column, query, 1) DESC`.
5.  **Highlight:** `SELECT ts_headline(...)` on the final LIMITed rows.

**The Golden Rule:**
*If your `WHERE` clause contains `LIKE '%...%'` and the table has more than 10,000 rows, you are doing it wrong. Use FTS.*
