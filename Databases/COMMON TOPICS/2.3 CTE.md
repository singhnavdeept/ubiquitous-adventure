# CTEs (WITH Clauses): Temporary Named Result Sets That Transform Your SQL

## What is a CTE?

A **Common Table Expression (CTE)** is a temporary, named result set that exists only during the execution of a single SQL statement. You define it using the `WITH` clause at the top of your query.

Think of it as a **view that lives only for one query** – or a **named subquery** that can be referenced multiple times and, in the recursive case, can reference itself.

---

## Part 1: Non‑Recursive CTE (The 95% Use Case)

### Syntax
```sql
WITH cte_name AS (
    -- Your subquery here
    SELECT column1, column2
    FROM some_table
    WHERE condition
)
SELECT *
FROM cte_name
-- You can also JOIN multiple CTEs or the same CTE multiple times
```

### Why Use a CTE Instead of a Subquery?

| Aspect | Subquery | CTE |
|--------|----------|-----|
| **Readability** | Inline, can get nested deeply | Linear, top‑down flow |
| **Reusability** | Must copy‑paste if used multiple times | Can be referenced many times in the main query |
| **Recursion** | Impossible | Supported |
| **Optimization** | Same (in modern DBs) | Same (treated like subquery or inlined) |

### Example 1: Simple CTE
```sql
WITH high_value_orders AS (
    SELECT customer_id, SUM(amount) AS total
    FROM orders
    WHERE status = 'completed'
    GROUP BY customer_id
    HAVING SUM(amount) > 10000
)
SELECT c.name, h.total
FROM customers c
JOIN high_value_orders h ON c.id = h.customer_id;
```

### Example 2: Multiple CTEs in One Query
```sql
WITH 
active_customers AS (
    SELECT id, name FROM customers WHERE active = true
),
recent_orders AS (
    SELECT customer_id, SUM(amount) AS last_month_total
    FROM orders
    WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'
    GROUP BY customer_id
)
SELECT a.name, r.last_month_total
FROM active_customers a
LEFT JOIN recent_orders r ON a.id = r.customer_id;
```

### Example 3: CTE Used Twice (Self‑Join)
```sql
WITH employees_with_salary AS (
    SELECT id, name, salary, manager_id FROM employees
)
SELECT 
    e.name AS employee,
    m.name AS manager
FROM employees_with_salary e
LEFT JOIN employees_with_salary m ON e.manager_id = m.id;
```

### Performance Note
In most databases (PostgreSQL, MySQL 8+, SQL Server, Oracle), a CTE is **not materialized by default** – it’s like a subquery that gets inlined. If you reference the same CTE multiple times, it will be executed multiple times unless you materialize it (e.g., `MATERIALIZED` keyword in PostgreSQL). Use `MATERIALIZED` if the CTE is expensive and used more than once.

```sql
-- PostgreSQL: force materialization
WITH expensive_cte AS MATERIALIZED (
    SELECT ... FROM huge_table
)
SELECT * FROM expensive_cte e1 JOIN expensive_cte e2 ...
```

## Part 2: Recursive CTE – When a Query References Itself

### Purpose
Recursive CTEs allow you to query **hierarchical or graph‑structured data** – think org charts, bill of materials, folder trees, network paths, or any self‑referencing table (e.g., `employee_id`, `manager_id`).

### Syntax (5 mandatory parts)
```sql
WITH RECURSIVE cte_name AS (
    -- Anchor member (non‑recursive, base result)
    SELECT columns
    FROM table
    WHERE condition   -- the starting point(s)
    
    UNION ALL        -- (or UNION if you need unique rows)
    
    -- Recursive member (references the CTE itself)
    SELECT columns
    FROM table t
    JOIN cte_name r ON t.parent_id = r.id
    -- termination condition is implicit when no more rows returned
)
SELECT * FROM cte_name;
```

### How It Works (Step‑by‑Step)
1. Execute the **anchor member** → result set = initial rows.
2. Execute the **recursive member**, using the current contents of the CTE as a “working table”.
3. Repeat step 2 until the recursive member returns **no new rows**.
4. Combine all results (anchor + all recursive iterations) via `UNION ALL` (or `UNION`).
5. Return the final result set.

### Example 1: Org Chart – Find All Subordinates (Downward Traversal)
```sql
WITH RECURSIVE org_tree AS (
    -- Anchor: start with the CEO (no manager)
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive: find all employees whose manager is already in the CTE
    SELECT e.id, e.name, e.manager_id, ot.level + 1
    FROM employees e
    JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT * FROM org_tree ORDER BY level, name;
```

### Example 2: Upward Traversal – Find All Ancestors of an Employee
```sql
WITH RECURSIVE report_chain AS (
    -- Anchor: start with a specific employee
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE id = 42
    
    UNION ALL
    
    -- Recursive: go up to the manager
    SELECT e.id, e.name, e.manager_id, rc.depth + 1
    FROM employees e
    JOIN report_chain rc ON e.id = rc.manager_id
)
SELECT * FROM report_chain;
```

### Example 3: Generate a Series of Numbers (Simple Recursion)
```sql
WITH RECURSIVE numbers AS (
    SELECT 1 AS n
    UNION ALL
    SELECT n + 1 FROM numbers WHERE n < 10
)
SELECT * FROM numbers;
```
Output: 1,2,3,…,10.

### Important Rules & Limitations
- **`RECURSIVE` keyword** is required (SQL standard; MySQL, PostgreSQL, SQL Server need it; Oracle omits it but still uses recursive CTE syntax).
- **`UNION ALL` vs `UNION`**:
  - `UNION ALL` is faster and preserves duplicates (often fine for hierarchies).
  - `UNION` removes duplicates but can hide cycles (not recommended for tree traversal unless you need unique rows).
- **Termination** – you must ensure the recursive member eventually stops. Usually this happens naturally when no more rows join (e.g., no more managers). But you can also add a `WHERE` clause with a depth limit.
- **Infinite loops** – if your data has a cycle (e.g., A manages B, B manages A), a recursive CTE without cycle detection will run forever. Most databases have a `MAXRECURSION` setting (SQL Server) or you must implement cycle detection manually.

### Cycle Detection (Safe Recursive CTE)
Use an **array or path column** to track visited nodes.

```sql
WITH RECURSIVE graph AS (
    SELECT id, name, ARRAY[id] AS path, false AS is_cycle
    FROM nodes
    WHERE id = 1
    
    UNION ALL
    
    SELECT n.id, n.name, path || n.id, n.id = ANY(path)
    FROM graph g
    JOIN edges e ON g.id = e.from_id
    JOIN nodes n ON e.to_id = n.id
    WHERE NOT g.is_cycle
)
SELECT * FROM graph WHERE NOT is_cycle;
```

## Common Use Cases Summary

| Scenario | CTE Type | Example |
|----------|----------|---------|
| Break down a complex query into steps | Non‑recursive | `WITH sales_summary AS (...) SELECT ...` |
| Use same subquery multiple times | Non‑recursive | `WITH data AS (...) SELECT * FROM data d1 JOIN data d2` |
| Replace a subquery in `FROM` for clarity | Non‑recursive | Any moderate‑complexity subquery |
| Org chart / tree traversal | Recursive | `WITH RECURSIVE org AS (...)` |
| Graph pathfinding (simple) | Recursive | Employee manager chain, folder parent hierarchy |
| Generate sequence of dates | Recursive | `WITH RECURSIVE dates AS (SELECT '2025-01-01'::date AS dt UNION ALL SELECT dt+1 FROM dates WHERE dt < '2025-12-31')` |
| Parse nested JSON / XML (some DBs) | Recursive | Flattening recursive structures |

## CTEs vs. Temporary Tables vs. Subqueries

| Feature | CTE | Temp Table (`CREATE TEMP TABLE`) | Subquery |
|---------|-----|----------------------------------|----------|
| Scope | Single query | Session or transaction | Single query |
| Can be indexed | No (unless materialized) | Yes | No |
| Reuse in same query | Yes (multiple references) | Yes (any number of queries) | No (must rewrite) |
| Recursion | Yes (recursive CTE) | No (without procedural code) | No |
| Performance | Inlined by default (can be materialized) | Explicit, can be tuned | Inlined |
| Best for | Medium complexity, recursion, readability | Heavy, repeated use across many statements | Simple one‑off logic |

## Pitfalls & Best Practices

### ❌ Common Mistakes
1. **Forgetting `RECURSIVE` keyword** – results in syntax error (except Oracle).
2. **Infinite recursion** – caused by cycles or missing termination condition. Always consider a `MAXRECURSION` hint or depth limit.
3. **Using `ORDER BY` inside the CTE** – usually not allowed (or ignored) except in some DBs with `TOP`/`LIMIT`. Apply ordering in the outer query.
4. **Assuming CTE is materialized** – it often isn’t. If you reference it multiple times, you may be executing the subquery multiple times. Check your DB’s behavior.
5. **Over‑nesting CTEs** – while you can chain CTEs (`WITH a AS (...), b AS (SELECT ... FROM a)`), deep chains hurt readability. Break into multiple statements or use temp tables.

### ✅ Best Practices
- **Name CTEs meaningfully** – not `cte1`, `cte2`, but `high_value_customers`, `monthly_sales_agg`.
- **Use CTEs to flatten nested subqueries** – compare:
  ```sql
  -- Hard to read
  SELECT * FROM (SELECT * FROM (SELECT ...) x) y;
  
  -- Much better
  WITH step1 AS (...), step2 AS (SELECT ... FROM step1)
  SELECT * FROM step2;
  ```
- **Test recursion with a depth limit first** – add `WHERE depth <= 10` in the recursive member to avoid accidental infinite loops during development.
- **Prefer `UNION ALL`** unless you explicitly need to eliminate duplicates (rare in hierarchies).
- **Document recursive CTEs** – explain the anchor, the relationship, and the termination condition in comments.

## Database Dialect Notes

| Database | Syntax | Recursive keyword | Cycle detection helpers |
|----------|--------|-------------------|--------------------------|
| PostgreSQL | `WITH RECURSIVE` | Required | `CYCLE` clause (v14+), or manual array |
| MySQL | `WITH RECURSIVE` | Required (8.0+) | Manual array using `JSON_ARRAY_APPEND` |
| SQL Server | `WITH` (no keyword for recursive?) Actually `WITH ...` works, but recursion is implied by self‑reference. Must set `OPTION (MAXRECURSION n)` | Implicit | `MAXRECURSION` hint |
| Oracle | `WITH` (no `RECURSIVE` needed) | Not needed | `CONNECT BY` is older; recursive CTE works with `CYCLE` clause |
| SQLite | `WITH RECURSIVE` | Required | Manual path column |

## Final Pro Tips from the Field

1. **Use recursive CTEs for any tree with unknown depth** – like `category` hierarchies or `comment` threads.
2. **If your query has more than 3 subqueries, reach for a CTE** – your future self will thank you.
3. **Recursive CTEs are not the fastest for very deep trees** – for millions of nodes, consider a materialized path or closure table.
4. **You can `INSERT`/`UPDATE`/`DELETE` using a CTE** (in PostgreSQL, SQL Server, others):
   ```sql
   WITH deleted AS (DELETE FROM logs WHERE created_at < '2024-01-01' RETURNING *)
   SELECT count(*) FROM deleted;
   ```
5. **Always put the outer `SELECT` after the CTE definition** – the CTE itself is just a definition; you need a final statement to actually run something.
